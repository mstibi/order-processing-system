# M7 Load + CI (izmjereno u Dockeru 2026-10-16; CI čeka push na GitHub)

## Što je napravljeno (datoteke)
- `load/orders.js`: k6 skripta. `constant-vus` (default 50 virtualnih korisnika, 30 s), svaki stalno šalje `POST /orders` s jedinstvenim `Idempotency-Key`. `check`: odgovor mora biti 201. `handleSummary` sprema `requests`, `rps`, `p50/p95/p99/max` u `results/load.json`.
- `load/seed.sql`: proizvod `id=1000000` s 100 000 000 komada, da zaliha ne utječe na mjerenje.
- `docker-compose.yml` servis `k6` (profil `load`, ne pali se s `docker compose up`): k6 radi **unutar compose mreže** i gađa `http://api:8000`.
- `.github/workflows/ci.yml`: digne stack, API testovi, fake-payments testovi, testovi oraclea (`scripts/`), `race.py` naive + atomic, `replay.py`, k6 smoke (10 VU, 10 s), upload `results/load.json`.

## Zašto ovako (odbačene alternative)
- **k6 u containeru za brojke u README-u**: k6 na Windows hostu ide kroz Docker Desktop/WSL2 port-forward, dodatni skok koji kvari p99. Plan: izmjeriti jednom oboje i razliku upisati u README.
- **Headline brojke s `FAIL_RATE=0 TIMEOUT_RATE=0`**: s timeoutima p99 = timeout (3 s), to mjeri fake-payments, ne naš kod. Run s greškama ide posebno.
- **CI ne pada na p99**: GitHub runneri su dijeljeni i bučni; CI provjerava samo točnost (`checks rate > 0.99`).
- **p99, ne prosjek**: prosjek sakrije rep. Ako je 1% zahtjeva sporo, a korisnik radi 100 zahtjeva po sesiji, skoro svaki korisnik doživi taj spori.

## Što je izmjereno (k6 2.3.0 u compose mreži, 50 VU, 30 s, 8 runova)
- Medijan: **129 rps, p50 357 ms, p99 825 ms**, 100% odgovora 201 PAID. Raspon 103-185 rps (Docker Desktop na Windowsima je bučan).
- Usko grlo: jedan uvicorn worker (84% CPU = jedna jezgra) i jedan "vrući" redak (svi kupuju isti proizvod, 10 sesija čeka row lock). Svježa baza daje istih ~130 rps kao baza s 15k narudžbi, znači nije rast podataka.
- `handleSummary` radi bez izmjene na k6 2.x. Zamka: Git Bash prepiše `-e OUT=/results/x.json` u Windows putanju; treba `MSYS_NO_PATHCONV=1`.
- Fali: CI zelen, tek kad Mateo pushne repo na GitHub (Q3).

## Pitanja za intervju
1. **Što je p99 i zašto ga gledaš umjesto prosjeka?**
   99% zahtjeva je brže od te vrijednosti. Prosjek sakrije spore zahtjeve; p99 pokazuje rep koji korisnici stvarno osjete, a u sustavu s više poziva po stranici rep brzo postane pravilo.
2. **Zašto load generator ne smije dijeliti CPU s API-jem bez ograničenja?**
   Ako je k6 zagušen, kasni sa slanjem i mjerenja izgledaju gora nego što API stvarno jest (k6 docs). Zato `cpus` limiti ili zaseban stroj, i napisati uvjete mjerenja uz brojke.
3. **1000 korisnika istovremeno, a pool ima 20 konekcija. Što se dogodi?**
   Zahtjevi čekaju u redu poola (do 10 s), baza vidi najviše 20 konekcija. Ako čekanje prijeđe 10 s, API vrati 503 + `Retry-After` umjesto da visi. Na vrućem retku (svi kupuju isti proizvod) ionako sve čeka na isti row lock, pa veći pool ne bi pomogao.
