# M4 Idempotency

## Što je napravljeno (datoteke)
- `api/app/main.py` `create_order()`: korak 1 i 6 iz blueprinta.
  1. `INSERT INTO idempotency_keys ... 'PROCESSING' ON CONFLICT (key) DO NOTHING RETURNING key`. Ako je vratio red, ovaj zahtjev "posjeduje" ključ i radi narudžbu.
  2. Ako nije: pročitaj postojeći red. Drugi hash → **422**. Još PROCESSING → **409** `request_in_progress`. COMPLETED → vrati **spremljeni** status + body.
  3. Na kraju spremi `{"status_code", "body"}` i stavi COMPLETED. Sprema se i 409 (nema robe) i 402 (odbijeno), kao Stripe.
- Hash = sha256 od `[customer_id, sortirani artikli]`, pa redoslijed artikala u JSON-u ne mijenja hash.
- Ako `reserve` pukne neočekivano (ništa nije commitano), ključ se briše da klijent može ponoviti.
- `api/tests/test_idempotency.py`: isti ključ 2x → isti odgovor, 1 narudžba, 1 naplata; drugi body → 422; PROCESSING → 409; redoslijed artikala; i odgovor "nema robe" se ponavlja iako je roba u međuvremenu stigla.
- `scripts/replay.py`: 25 istih zahtjeva odjednom + 25 jedan po jedan. Rezultat: `orders=1 charges=1`, drugi body → 422.

Dvije razine idempotencije: klijent → naš API (`Idempotency-Key` header), i naš API → payment provider (ključ = `order_id`). Druga razina štiti od dvostruke naplate i kad API sam ponavlja ili reconciler pita ponovno.

## Zašto ovako (odbačene alternative)
- **`INSERT ... ON CONFLICT DO NOTHING`** umjesto "SELECT pa INSERT": SELECT-pa-INSERT ima isti race kao naive u M3 (dva zahtjeva oba vide "nema ključa"). Primary key u bazi garantira da samo jedan INSERT uspije.
- **409 za PROCESSING umjesto čekanja**: čekanje bi držalo konekciju/request; Stripe također vraća 409 i klijent ponovi.
- **422 za isti ključ s drugim bodyjem**: to je bug kod klijenta, ne smije se tiho izvršiti ni vratiti tuđi odgovor.

## Poznata granica (napisano u README)
Ako API padne dok je ključ PROCESSING, ključ tamo ostaje i retry dobiva 409 zauvijek. Narudžbu ipak sredi reconciler, ali klijent ne dobije odgovor. Popravak (bonus): `locked_at` + preuzimanje ključa starijeg od N s (Brandur, "Implementing Stripe-like Idempotency Keys in Postgres").

## Pitanja za intervju
1. **Što je idempotencija i zašto je treba POST /orders?**
   Ponavljanje istog zahtjeva ima isti učinak kao jedno slanje. Mreža puca, klijent ne zna je li zahtjev prošao pa ponovi; bez idempotencije svaki retry = nova narudžba i nova naplata.
2. **Dva ista zahtjeva stignu u istoj milisekundi. Što se dogodi?**
   Oba rade `INSERT ... ON CONFLICT DO NOTHING`. Postgres primary key pusti samo jedan; drugi dobije 0 redaka, pročita PROCESSING i vrati 409. replay.py: 25 odjednom → 1 narudžba, ostali 409 ili spremljeni 201.
3. **Zašto spremaš i neuspješne odgovore (409, 402)?**
   Klijent mora dobiti isti odgovor za isti ključ. Da ne spremamo 409, retry nakon dostave robe bi odjednom napravio narudžbu, a klijent je već dobio "nema robe" i možda kupio drugdje.
