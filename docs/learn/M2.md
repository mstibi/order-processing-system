# M2 Happy path

## Što je napravljeno (datoteke)
- `api/app/main.py`: `POST /orders` (header `Idempotency-Key` obavezan), `GET /orders/{id}`.
- `api/app/orders.py`: `reserve()` = jedna transakcija: skini zalihu za svaki artikl, upiši `orders` (PENDING), `order_items`, `payments` red. Plus promjene statusa: `mark_paid`, `mark_unknown`, `cancel` (FAILED/CANCELLED + vraćanje zalihe).
- `api/app/payments.py`: `charge()` vraća `succeeded` / `declined` / `unknown`; `lookup()` pita providera što zna o narudžbi.
- `api/tests/test_orders.py`: 201 + PAID + točno 1 naplata; GET vraća isto; kupnja preko zalihe → 409 i ništa se ne mijenja; narudžba s 2 artikla gdje drugi nema zalihe → cijela se poništi (rollback); validacija → 422.

Tok: `reserve` (COMMIT) → plaćanje **izvan transakcije i bez posuđene konekcije** → upiši ishod → odgovor. Kodovi: 201 PAID, 402 FAILED, 202 PAYMENT_UNKNOWN, 409 nema robe.

## Zašto ovako (odbačene alternative)
- **Plaćanje izvan transakcije**: da je HTTP poziv unutar transakcije, red proizvoda bi bio zaključan do 3 s (timeout) i svi kupci tog proizvoda bi čekali. Konekcija bi bila zauzeta, pa 20 sporih plaćanja = prazan pool.
- **Artikli sortirani po `product_id` prije zaključavanja**: dvije narudžbe [A,B] i [B,A] bi inače mogle čekati jedna drugu zauvijek (deadlock).
- **Svaka promjena statusa ima `WHERE status = ANY(dopušteni)`**: API i reconciler mogu istovremeno raditi na istoj narudžbi; samo jedan dobije `rowcount == 1` i samo on vraća zalihu.
- **Cijena se kopira u `order_items.price_cents`**: kasnija promjena cijene ne mijenja staru narudžbu.

## Što bi se pokvarilo bez toga
- Bez jedne transakcije u `reserve`: ako drugi artikl nema zalihe, prvi bi ostao skinut (izgubljena roba).
- Bez provjere statusa u `cancel`: dvostruko vraćanje zalihe → zaliha raste iz ničega.

## Pitanja za intervju
1. **Zašto ne zoveš payment provider unutar DB transakcije?**
   Transakcija drži lockove i konekciju dok traje. Vanjski poziv može trajati sekundama ili visjeti; za to vrijeme nitko ne može kupiti isti proizvod i pool se prazni. Zato: kratka transakcija (zaliha + PENDING), COMMIT, plaćanje, pa nova kratka transakcija za ishod.
2. **Što ako API padne nakon COMMIT-a, a prije plaćanja?**
   Narudžba ostane PENDING, zaliha skinuta. Reconciler svakih 5 s traži PENDING starije od 60 s i pita providera: naplata postoji → PAID, ne postoji → CANCELLED + vrati zalihu. Bolje rješenje je outbox pattern (bonus faza).
3. **Kako sprječavaš deadlock kod narudžbe s više proizvoda?**
   Svi zaključavaju retke istim redoslijedom (sortirano po `product_id`). Deadlock je krug čekanja; s istim redoslijedom krug ne može nastati.
