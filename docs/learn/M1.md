# M1 Skeleton

## Što je napravljeno (datoteke)
- `docker-compose.yml`: 3 servisa: `postgres` (16, schema se učita iz `db/schema.sql` pri prvom startu), `fake-payments` (port 9000), `api` (port 8000). API čeka da Postgres bude *healthy* (`pg_isready`).
- `db/schema.sql`: 5 tablica iz blueprinta. `CHECK (stock >= 0)` na `products`, `CHECK` na dopuštene statuse narudžbe, parcijalni index samo za otvorene narudžbe (PENDING / PAYMENT_UNKNOWN) jer ih reconciler stalno traži.
- `api/app/main.py`: FastAPI app, `GET /health` (radi `SELECT 1`, znači provjerava i bazu); connection pool i reconciler se pale u `lifespan`.
- `api/Dockerfile` (+ HEALTHCHECK), `api/tests/test_health.py`, `api/tests/conftest.py` (svaki test briše sve tablice i resetira fake-payments).
- `fake-payments/`: glumi Stripe. Pamti `Idempotency-Key`; isti ključ = isti odgovor, nikad druga naplata. `FAIL_RATE`, `TIMEOUT_RATE`, `LATENCY_MS` se čitaju iz env-a.
- `.github/workflows/ci.yml`: digne compose, `curl /health`, pokrene testove oba servisa.
- `scripts/local_stack.py`: isti stack **bez Dockera** (Postgres 16 iz pip paketa `pgserver`), rezervni put kad Docker nije dostupan (brojke u README-u su iz Dockera).

## Zašto ovako (odbačene alternative)
- **psycopg 3 + ručni SQL, bez ORM-a**: vidiš točno koji SQL ide u bazu; na intervjuu objašnjavaš lockove i transakcije, ne ORM magiju.
- **async (`AsyncConnectionPool`, `httpx.AsyncClient`)**: API većinu vremena čeka (bazu, plaćanje). Sync verzija bi držala thread dok čeka 3 s na plaćanje, a FastAPI ima samo ~40 threadova.
- **Pool `min 10 / max 20`, `autocommit=True`**: Postgres default `max_connections = 100`; 1000 zahtjeva ne treba 1000 konekcija, ostali čekaju u redu poola (do 10 s, onda 503). `autocommit=True` znači: svaka naredba se odmah commita, osim unutar `async with conn.transaction()`. Tako su transakcije uvijek eksplicitne u kodu.
- **Schema u `docker-entrypoint-initdb.d`** umjesto migracijskog alata (Alembic): jedna datoteka, dovoljno za v1. Mana: izmjena sheme traži `docker compose down -v`.

## Što bi se pokvarilo bez toga
- Bez `CHECK (stock >= 0)`: bug u kodu bi tiho spremio negativnu zalihu. S njim baza odbije zapis.
- Bez healthchecka i `depends_on: service_healthy`: API se digne prije baze i pukne pri otvaranju poola.
- Bez `max_size` na poolu: psycopg ga drži fiksnim na `min_size` (zamka iz docs-a).

## Pitanja za intervju
1. **Zašto connection pool, a ne nova konekcija po zahtjevu?**
   Otvaranje konekcije na Postgres je skupo (novi proces na serveru, TCP, auth). Pool drži nekoliko otvorenih i posuđuje ih. Postgres ima limit konekcija (default 100), pa pool ujedno štiti bazu: višak zahtjeva čeka u redu umjesto da obori bazu.
2. **Što radi `/health` i zašto dira bazu?**
   Vraća `{"status":"ok"}` samo ako može izvršiti `SELECT 1` kroz pool. Tako Docker healthcheck / load balancer zna da API stvarno može raditi, a ne samo da proces živi.
3. **Što je `lifespan` u FastAPI-ju?**
   Kod koji se izvrši jednom pri startu (prije prvog zahtjeva) i jednom pri gašenju. Ovdje: otvori pool, pokreni reconciler kao background task; pri gašenju ga otkaži i zatvori pool.
