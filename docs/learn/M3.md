# M3 Oversell bug + dva popravka

## Što je napravljeno (datoteke)
- `api/app/orders.py`: tri načina skidanja zalihe: `take_naive` (bug namjerno), `take_atomic` (API ga koristi), `take_for_update`. `reserve(..., mode=...)` bira jedan.
- `scripts/race.py`: napravi novi proizvod, pusti N kupaca odjednom (svaki kupuje 1 kom) kroz **istu `reserve()` funkciju kao API**, ispiše `sold`, `stock`, `oversold`, `lost_updates`, vrijeme; na kraju obriše svoje narudžbe.
- `results/race.txt`: sirovi ispis svih mjerenja (5 ponavljanja po modu).

```
naive:      SELECT stock;  if stock >= 1: UPDATE SET stock = <broj izračunat u Pythonu>
atomic:     UPDATE products SET stock = stock - 1 WHERE id = ? AND stock >= 1   (0 redaka = nema robe)
for_update: SELECT stock ... FOR UPDATE;  if stock >= 1: UPDATE SET stock = stock - 1
```

## Rezultat (lokalno, 1000 kupaca, 50 DB konekcija)
naive sa zalihom 100: **prodano 1000** (oversell 900), a baza i dalje kaže da ima 65-81 komad. atomic i for_update: uvijek `sold=100 stock=0`. Tablica u README-u.

## Zašto ovako (odbačene alternative)
- **race.py ide direktno na bazu (ne kroz HTTP)**: mjeri samo ono što se testira (zaključavanje), bez HTTP šuma, a koristi isti kod kao API. Kroz API bi ionako u bazi istovremeno bilo najviše 20 kupaca (pool).
- **Naive ne može oboriti `CHECK (stock >= 0)`**: piše apsolutni broj (`stock = 99`), nikad negativan. Zato bug prolazi tiho, bez ikakve greške. Baš to ga čini opasnim.
- **SERIALIZABLE nije potreban**: na READ COMMITTED Postgres nakon čekanja na lock ponovno provjeri `WHERE stock >= 1` na novoj vrijednosti. SERIALIZABLE bi kod 1000 kupaca na jednom retku dao gomilu `40001` grešaka i retryja.

## Što bi se pokvarilo bez toga
"Lost update": dva kupca pročitaju 100, oba upišu 99. Prodano 2, zaliha pala za 1. Ponovi 1000 puta → prodaš 10x više nego imaš.

## Pitanja za intervju
1. **Što je race condition i kako si ga reproducirao?**
   Rezultat ovisi o tome kojim se redom istovremene operacije izvrše. `race.py --mode naive`: 1000 istovremenih kupaca, svaki pročita zalihu, provjeri u Pythonu i zapiše novu vrijednost. Između čitanja i pisanja drugi pročitaju istu staru vrijednost, pa se prodaje prepisuju: prodano 1000 komada od 100.
2. **Row lock (FOR UPDATE) ili atomarni conditional UPDATE, kad koji?**
   Atomarni UPDATE kad se provjera da napisati u WHERE (`stock >= q`): jedna naredba, jedan round trip, lock najkraće traje. FOR UPDATE kad moraš pročitati redak i u kodu odlučiti nešto složenije prije pisanja. Oba su točna; atomic je bio malo brži (median 0.92 s vs 0.98 s za 1000 kupaca / 100 kom, lokalno).
3. **Zašto je atomarni UPDATE siguran na READ COMMITTED?**
   UPDATE zaključa redak. Drugi UPDATE na isti redak čeka da prvi commita, a onda ponovno izračuna WHERE na novoj verziji retka. Ako `stock >= q` više ne vrijedi, ažurira 0 redaka → 409. Nema prozora između provjere i pisanja jer su u istoj naredbi.
