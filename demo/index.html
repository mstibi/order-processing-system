Order processing system · live demo

An online shop backend that stays correct under pressure.

It never sells more than it has in stock and never charges a customer twice, even when 1000 people click at once or the payment provider stops answering.

Every button below runs a real test against the real system (API, PostgreSQL database and a fake payment provider) and shows the numbers that come back.

Demo 1

Overselling

A product has 100 items in stock. 1000 buyers press “Buy” at the same moment. Each one should get an item only if one is left.

Race condition: two buyers both read “1 left” before either of them writes “0 left”, so both buy it. Overselling is the result: the shop sells items it does not have.

Naive

Read the stock, check it in code, then write the new number. Looks fine, has the race condition.

Atomic UPDATE

Check and subtract in one database step: stock - 1 … WHERE stock ≥ 1. What the API uses.

SELECT FOR UPDATE

Lock the product row first, so other buyers wait in line, then check and subtract.

Demo 2

Same click, many times

People double-click, and phones resend requests on bad Wi-Fi. Here one customer sends the same order many times: half at the same instant, half one after another.

Idempotency key: a unique ID the client attaches to “this one purchase”. The server remembers it, so every repeat gets the first answer back instead of creating a new order and a new charge.

Demo 3

When payments fail

The payment provider sometimes declines a card, and sometimes does not answer at all. Many customers order at once; when a request gets no answer, the client retries it with the same idempotency key.

A timeout does not mean the payment failed: the money may already have moved. So the order is marked PAYMENT_UNKNOWN, and the reconciler, a background job that runs every 5 seconds, asks the provider what really happened and fixes the order.
